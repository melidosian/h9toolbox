# TD-H9 APRS code map (work in progress)

This is a map of **observed code in two shipped binaries**, not manufacturer source. Addresses for the main application use the inferred load base `0x01E00100`; the separate APRS image uses its vector-table base `0x08002000`. Ghidra's Pi32v2 processor module is incomplete, so main-application decompilation can be wrong around unsupported instructions. These findings are for offline analysis only.

The first compilable replacement core is in [replacement-source](../replacement-source/README.md). It separates observed serial and command behavior from the new APRS mute and TX verification policies. It is host tested and does not yet build either target firmware image.

The APRS stock image is 17,304 bytes (SHA-256 `1dbbc10425f186f22a4d82d73f139f1e3cc3388931b73eb8ed18b6e3087ccd33`), with initial stack pointer `0x20001A50` and reset vector `0x080020D5`. `replacement-source/link_aprs_check.py` uses those observed values as a diagnostic link envelope for all 11 replacement APRS objects. The linked ELF has an inert reset handler and is not an update image; production startup, board drivers, and a validated memory map are still absent.

## Separate APRS-1.0.15 controller

The Cortex-M image was imported into Ghidra as `ARM:LE:32:Cortex` at `0x08002000`. The following paths are supported by both caller references and decompilation:

| Address | Observed role |
| --- | --- |
| `0x08002EF8` | ADC callback reads a sample through `0x08002F82`, calls receive demodulator `0x08002308`, then conditionally calls the TX waveform generator `0x08002468`. |
| `0x08002308` | Receive demodulator; a five-sample delay, correlation/filter, and timing recovery feed the recovered-bit path at `0x080055C4`. The selected decompilation and state initialization at `0x08002604` are in `evidence/aprs-demod-init.txt`; the source port is in `../replacement-source/aprs/h9_aprs_demod.c`. Ideal software loopback now recovers a generated packet; recorded audio and radio hardware remain unverified. |
| `0x08002468` | Transmit waveform scheduler reads a 64-byte queue, sends flag bytes, shifts data bits LSB first, changes the 0x40/0x75 oscillator step for NRZI zero bits, inserts a zero after five data one bits, and produces eight DAC samples per bit. |
| `0x08002664` / `0x08005150` | First queued transmit byte starts waveform state; settings at RAM `0x20000110` and `0x20000114` become rounded lead and tail flag counts through `(setting * 1200 + 4000) / 8000`. Later queued bytes refresh the tail count. |
| `0x0800530C` / `0x0800534C` | Packet-to-queue encoder emits an opening flag, escapes `0x7E`/`0x7F`/`0x1B`, updates the reflected CRC, emits complemented FCS low byte then high byte, and closes with a flag. |
| `0x0800211C` / `0x08005760` | Transmit send gate checks channel-busy state and an 8-bit draw from `state = state * 0x41C64E6D + 0x3039` against a persistence threshold before calling the encoder. Its busy branch polls receive state and can end without sending. A cooperative decision step is ported; hardware signal mapping, timing, and PTT remain unverified. |
| `0x0800555C` | Sends an assembled received frame to the main radio through `0x080048F4`. |
| `0x080051FC` | Drains the recovered-byte queue, assembles a frame between `0x7E` flags, handles `0x1B` escaping, caps payload plus FCS at `0x318` bytes, and accepts frames longer than 17 bytes only when the running CRC equals `0xF0B8`. |
| `0x08006028` | CRC table update. The 256-entry stock table at `0x08006158` matches reflected polynomial `0x8408`, initialized to `0xFFFF`. |
| `0x08005180` / `0x08005830` | Valid-frame callback forwards to the main radio as command `0x00` with the last two FCS bytes removed. |
| `0x08004894` | Sends a serial frame bounded by `0xC0`, escaping `0xC0` as `0xDB 0xDC` and `0xDB` as `0xDB 0xDD`. |
| `0x08005B8C` | Parses incoming serial frames and dispatches command bytes. |
| `0x08002A4C` | Accepts a packet for the TX path, then calls `0x08002C94`, which passes it to `0x0800476C`. |
| `0x080029D0` / `0x080029E4` | Clear/set GPIO port at `0x50000400`, mask `0x20`; the circuit meaning of this pin is unverified. |

The parser at `0x08005B8C` uses these command IDs (direction is **main radio to APRS controller**):

| Command | Observed handler |
| --- | --- |
| `0x00` | The dispatch jump table reaches `0x08005BCC`, which calls send gate `0x08005760` with the serial payload and length. The gate eventually invokes packet encoder `0x0800534C`. |
| `0x10` | Sends the frame payload back through `0x080048F4` when nonempty. The caller's intended semantics need more study. |
| `0x11` | Subcommand `1` calls `0x080029E4` (set GPIO mask `0x20`); `2` calls `0x080029D0` (clear); `3` calls `0x08002964` (read pin) and reports a byte; `4` passes the remainder to `0x08002A4C` (packet TX path). |
| `0x13` | Calls `0x0800586C`, which returns a 48-byte status/configuration payload. |
| `0x20` | Calls `0x08005AAC`, which returns version information (`V1.0.15` and `V1.0.0` strings). |

In the opposite direction, `0x080048F4` wraps `0x08004894` with command `0x10`; one of its callers is the received-frame sender at `0x0800555C`. The handler's source and destination may share command numbers; do not infer the same semantics in both directions.

The ADC callback calls the demodulator before its TX/no-TX branch. The demodulator feeds the frame parser, which CRC-checks and forwards received packets to the main radio. This shows that the separate processor has an independent receive-processing path; it does **not** prove which analog signal the main radio feeds into its ADC, or where the speaker is gated. Disabling this ADC path would defeat packet decoding. A correct APRS mute would leave it active.

The transmit scheduler and its queue producer are decompiled in `evidence/aprs-tx-wave-scheduler.txt` and `evidence/aprs-tx-queue-producer.txt`; the packet encoder and send gate are in `evidence/aprs-tx-packet-encoder.txt` and `evidence/aprs-tx-send-gate.txt`. The replacement source now connects the serial packet request, cooperative gate, packet encoder, and waveform scheduler in an owned-memory service. Its generated samples decode back to the same packet in an ideal host loopback. Carrier sensing, PTT control, and physical ADC/DAC routing have not been connected or measured. This is not a validated RF transmitter.

## Main Pi32v2 application v1.0.38

Ghidra-JieLi was installed in a portable Ghidra 12.1.4 copy, and the stock `app.bin` was imported as `pi32v2:LE:32:default` at `0x01E00100`. The project currently has 1,918 recognized functions after seeding selected entrypoints. This count is an analyzer artifact, not a source-function count.

| App offset | Virtual address | Observed role |
| --- | --- | --- |
| `0x042E24` | `0x01E42F24` | Programs DAC control registers around `0x001E2F00` based on an audio structure. |
| `0x04314C` | `0x01E4324C` | Initializes/queries DAC state; called from `0x01E610F0`. |
| `0x043434` | `0x01E43534` | Configures DAC rate, buffers, and per-channel values. |
| `0x060F7E` | `0x01E6107E` | Audio initialization and stored settings reads; calls `0x01E4324C`. |
| `0x08A840` | `0x01E8A940` | Clears DAC and ADC control bits in a broad shutdown routine. |
| `0x0592E4` | `0x01E593E4` | Writes `0x6040 | (mode << 8)` to radio register `0x47` through `0x01E5070A`; confirmed by Ghidra and linear Pi32 disassembly. |
| `0x05CB2C` | `0x01E5CC2C` | Receive-setup path writes radio register `0x30`, selects AF mode `1`, then writes register `0x70`. |
| `0x05224C` | `0x01E5234C` | Audio output request/arbitration. Its decompilation calls the gate at `0x01E52328`, but some decompiled conditions are invalid because of incomplete Pi32 semantics. |
| `0x052228` | `0x01E52328` | Sends the requested value to `0x01E001D2` with pin/index `3`, then records the **requested** bit 0 in RAM `0x00011B4D`. Physical speaker wiring is not yet confirmed. |
| `0x0000BA` | `0x01E001BA` | Maps a GPIO index to a register bank through the table at app+`0x000554`. Index `3` selects the first bank, `0x001E5000`. |
| `0x0000D2` | `0x01E001D2` | Generic GPIO output writer. Independent Pi32 decoding shows the selected output bit is `1 << (index & 0xF)`; for index `3` this is bit `3` of the first GPIO bank's output register. |

These are generic audio routines. None yet has a confirmed APRS-specific branch or a CH-A/CH-B speaker gate. The APRS string hits around app offset `0xCC000` are language resources, not function names. The CHIRP clone-image offsets for APRS settings are useful for locating stored data but do not identify code addresses.

The register-`0x47` expression matches [BK4819 AF selection code in an open firmware implementation](https://github.com/psck/uv-k5-firmware-pmr/blob/main/driver/bk4819.c), where mode `0` is mute and mode `1` is FM audio. This is a **cross-device interpretation** of the TD-H9 bytes, not proof of the TD-H9 board wiring. The TD-H9's calls with mode `1` in receive setup and mode `3` in a tone path support it. Muting register `0x47` could also remove the analog signal feeding the separate APRS controller, so it is not a safe patch target yet. The `0x01E52328` on/off path is a local-speaker candidate, but the hardware probe showed that Bluetooth audio bypasses it.

`trace_pi32.py` walks direct Pi32 calls and branches from 1,918 Ghidra function starts. On this stock image it decoded 78,145 instruction addresses and indexed 1,558 direct-call targets. It recovered the known call from app+`0x060FF0` to app+`0x04314C`, which independently checks the relative-call calculation. The index is incomplete at indirect jumps and unrecognized code, and it does not imply that every indexed target is a function start. It found six direct callers of the AF selector at app+`0x0592E4`: `0x0594A8`, `0x05956E`, `0x05A9AC`, `0x05AA3A`, `0x05CB54`, and `0x05CC10`.

The same index found ten direct call sites to the audio request at app+`0x05224C`. Ghidra places two of them in tone-sequence routines: `0x01E5AB5A` and `0x01E5AC94` request `(8, 1)` before producing tones and `(8, 0)` afterward, then restore radio AF mode `1`. The receive setup at `0x01E5CC2C` requests `(4, 0)` after selecting AF mode `1`, and a later receive-state routine at `0x01E5CDEC` requests `(2, 1)` under a state condition. These callers support a shared speaker/audio arbitration role. They do not identify a per-channel APRS mute point, and the current Pi32 decompiler still misrenders some branches and arguments. The read-only report is in ignored `output/stock/gate-callers.txt`.

The GPIO result has an important decoder cross-check: Ghidra renders `0x01E001D2` with an impossible `index > 0x40 && index < 0x38` condition. The independent Pi32 decoder instead shows an early return when the index exceeds `65`, followed by the normal bank lookup and output write. The stock table entries at app+`0x000554` are `0x001E5000`, `0x001E5040`, `0x001E5080`, and `0x001E50C0`. In the audio path, `0x01E52328` supplies index `3`, so the requested on/off value reaches bit 3 at `0x001E5000`. This establishes the firmware register operation, **not** the physical connection to the speaker amplifier or the APRS controller. The independent disassemblies are in ignored `output/stock/gpio-base.asm` and `gpio-write.asm`.

Independent disassembly of `0x01E5234C` also shows an early return when its stored requested state matches the new request. The state read at virtual `0x01E52354` is RAM `0x00011B4D` (`0x11AD0 + 125`), whereas Ghidra labels it `DAT_000121DD` in the decompilation. The caller therefore may never invoke the patched GPIO writer during an interval of ordinary reception. This limits the low-write probe: normal speaker audio under the probe does not establish GPIO polarity or disprove the speaker-gate hypothesis. The disassembly is in ignored `output/stock/audio-gate-control.asm`.

One audio-arbitration state byte, RAM `0x00012BF4`, is also read by `0x01E55D44` before drawing the `All Lock` UI message. It is therefore a lock-state flag, not evidence of the APRS RX channel. The main channel-selection state is still unlocated.

Additional read-only references narrow two channel candidates. With the corrected SLEIGH byte-load offset, `0x01E50F58` returns RAM byte `0x00011B1D` when `0x00011B1E` is nonzero; otherwise it returns bit 7 of `0x00011B50`. Its callers draw the A/B frequency display, so the return value has A/B presentation semantics. `0x01E5CCCA` also branches on `0x00011B1D` in a receive/tone setup path. Neither reference proves which RF channel is feeding the APRS decoder. `0x00012BAD` controls FM-radio versus transceiver display branches, so it is not an APRS RX channel selector. The corrected decompilation is in ignored `output/stock/channel-flags-fixed-sleigh.txt`. The original `channel-flags-refs.txt` and `channel-receive-inventory.txt` contain wrong RAM labels for affected byte loads and should not be used to infer those addresses.

The main application's **outgoing** APRS packet route is now identified. `FUN_01e5b398` (app+`0x05B298`) assembles up to 512 bytes of AX.25 data using the seven-byte address encoder at app+`0x05B24A`, control byte `0x03`, and a PID default of `0xF0`. Its wrapper at app+`0x05B3EA` passes a successful packet to app+`0x05B3BE`. The framer at app+`0x05B32E` emits five leading `0xC0` bytes, a command byte, `0xDB 0xDC`/`0xDB 0xDD` escapes, and three trailing `0xC0` bytes, requiring an output capacity of at least `2 * packet_length + 10`. The wrapper supplies command `0x00` and a 2,048-byte buffer, then calls the UART function pointer from the structure rooted at RAM `0x00011AD0` (pointer at `0x00011CFC`, slot `+20`). Independent stock-hash-checked disassembly is in `evidence/stock/aprs-main-ax25-address.asm`, `aprs-main-wire-framer.asm`, and `aprs-main-wire-sender.asm`. The port is in `replacement-source/main/h9_main_ax25.*` and `h9_main_aprs_wire.*`; an ideal host loopback passes its packet through the separate APRS source and recovers it. The actual UART driver, RF path, and hardware timing are still unverified.

The main application's **incoming** APRS-module path is the ring-buffer receiver at app+`0x087218`, with a four-state `0xC0`/`0xDB` frame parser at app+`0x087340`. It stores a command byte, then up to 1,024 decoded payload bytes; `0xDB 0xDC` and `0xDB 0xDD` decode to `0xC0` and `0xDB`. Unlike the APRS controller's incoming parser, this main parser accepts an otherwise unknown byte after `0xDB` literally. A completed frame calls the dispatcher at app+`0x0870BC` with command and length. That dispatcher branches on `0x00`, `0x10`, `0x11`, `0x21`, and `0x51`. The stock-hash-checked independent decode is in `evidence/stock/aprs-main-wire-receiver.asm`; the framing state machine is ported in `replacement-source/main/h9_main_aprs_receive.*`. The dispatcher and UART driver are not yet ported.

`H9FrameCandidates.java` previously scanned recognized Pi32 functions for the APRS controller's `0xC0`/`0xDB` framing constants and missed this outgoing framer because its entry point was not recognized. The main application's **incoming** APRS serial parser remains unidentified; the short scan candidates were unrelated initialization/UI code, and the large candidate has unreliable function boundaries. This negative result is limited by the incomplete Pi32 processor module and possible framing in another unrecognized routine.

## APRS mute and unexpected CH-A TX

The first requested change is silence for APRS bursts on **both the built-in speaker and Bluetooth audio while retaining decoding/display**. A plausible hook is in the main application's per-channel receive-audio routing after the signal feeding the APRS controller is tapped but before the audible paths split. The current analysis identifies a radio AF selector and a local-speaker on/off request, but has not shown which signal goes to the APRS controller ADC, where Bluetooth receives audio, or whether an audible gate is channel-specific. The generic DAC routines are too global: changing them could mute CH-A voice, alerts, or both channels.

The corrected receive-audio export (`evidence/stock/bt-audio-candidates-fixed.txt`) shows `FUN_01e52202` (app+`0x052102`) evaluates several receive and channel-state bytes before the audio request reaches `FUN_01e52328`/GPIO3. That makes it useful for understanding when the built-in speaker is requested, but it provides no demonstrated Bluetooth gate or APRS decoder tap. The separate APRS image's ADC callback (`FUN_08002ef8`) sends each sample to its demodulator before its TX branch; a mute at the ADC input would also defeat decoding. The next useful boundary is the main radio AF source versus the APRS ADC feed and the Bluetooth feed, not another unconditional GPIO3 patch.

The independent Pi32 decode now finds a direct `APRS RX CH` read at app+`0x086180`: base `0xC0F0` plus `1090` reads RAM `0x0000C532`, matching clone offset `0x3116`. The enclosing routine at app+`0x086138` compares the working receive frequency in RAM `0x00011C8C` with the stored A/B frequencies at `0x00011CA0`/`0x00011CA8`, maps a match to side `0`/`1`, and compares that side with setting `1`/`2` respectively. A direct call at app+`0x0870FE` follows a packet-type check in its caller. This is a **packet-processing filter candidate**, not an identified audible gate: setting `0` skips this particular comparison, and earlier/later conditions may still stop decoding. See `evidence/stock/aprs-rx-channel-filter.asm` and `aprs-rx-filter-caller.asm`. It gives the APRS channel trace a concrete starting point without establishing where Bluetooth or the APRS ADC obtains audio.

The user observed CH-A key up on a voice repeater while APRS operated on CH-B. Later-reported settings included `APRS TX CH = CHB-Lock`, with both DIGI enables off, Timed Beacon off, and PTT Linkage off; those values were collected after the incident. The ARM parser shows a distinct transmit-packet command (`0x11` subcommand `4`), but it does not decide the RF channel. The channel selection and PTT routing are main-application tasks to trace. No flashable mod or safe patch offset has been established.

The [CHIRP TD-H9 test driver](https://chirpmyradio.com/attachments/16094/tdh8.py) maps the saved-image byte at `0x3117` to APRS TX CH, with `0=CHA-Lock`, `1=CHB-Lock`, `2=CHA-Auto`, `3=CHB-Auto`, and `4=CHA+CHB`. It maps `0x3116` to APRS RX CH (`0=Off`, `1=CH-A`, `2=CH-B`), `0x30F6` to PTT Linkage, `0x30F7` to Timed Beacon, `0x30F8..0x30F9` to its interval, `0x30FA` to DIGI Forward CH, and `0x30FB`/`0x3104` to the two DIGI enable bytes. `inspect_aprs_config.py` reads these fields from an existing 12,616-byte clone image; it sends nothing to the radio. All ten saved TD-H9 Normal images in Downloads from 11:48 through 14:50 on 2026-11-03 contain `TX CH=1` (CHB-Lock) and `RX CH=2` (CH-B), with PTT Linkage and both DIGI enables off. All ten also contain **Timed Beacon on, interval 60 seconds**. That historical setting could explain recurring APRS transmission, but does not explain why CH-A appeared to key with CHB-Lock. The user later reported Timed Beacon off, so a fresh screen check or clone capture is required before claiming its current state. The UI label `Lock` has no verified hardware semantics in the CHIRP mapping; a dummy-load test must distinguish manual, timed, and relay TX paths.

For the bench TX-channel check, the user attached a dummy load directly and set CH-A to 445.390 MHz, CH-B to 144.390 MHz, both simplex and Low power. The screen initially showed Timed Beacon on, Timing `1`, and `CH B-LOCK`. The user then changed Timing to `60` and reported Timed Beacon off before a controlled single-beacon trial. During the trial the screen went dark and no key-up was noticed, so the first result is inconclusive. Timed Beacon was requested off again while the display is set to Backlight Always On (Radio Setting item 12 per the TD-H9 manual); a second controlled observation awaits user confirmation. No RF frequency measurement has been made.
With Backlight Always On, the user repeated the one-beacon dummy-load observation. **The A line turned red while showing 445.390 MHz**, although APRS TX CH still read `CH B-LOCK`; the user turned Timed Beacon off afterward. This reproduces the unexpected A-side *display indication* under controlled settings. It does not independently measure the transmitted RF frequency.
For a comparison, the user temporarily turned Dual Watch **off** while CH-A was selected, kept the same dummy load, channels, `CH B-LOCK`, and 60-second beacon timing, then watched for 75 seconds. **Neither line turned red.** Timed Beacon was turned off and Dual Watch restored on afterward. This supports the Lock guard for the A-selected, non-Dual-Watch case and isolates the visible difference to Dual Watch behavior. It still does not tell us the actual RF frequency during the earlier A-red event.

The stock v1.0.38 main image now has a specific APRS TX decision point: `FUN_01e5c3d4` (app+`0x05C2D4`) checks RAM byte `0x0000C533` against five cases. The five-case switch order matches the CHIRP `APRS TX CH` enum, making this RAM byte a strong TX-channel-setting candidate. It reads bit 7 of RAM byte `0x00011B50` as a current channel state. Cases 0 and 1 return early when that bit disagrees with the corresponding lock choice; cases 2 and 3 temporarily set that bit to a chosen side, call `FUN_01e58e3e` to reconfigure the radio, then restore the original state after the packet. Case 4 keeps the current state. It writes the chosen side to `0x00011AEC`. `FUN_01e58e3e` reads that byte when Dual Watch (`0x00012BA7`, also used by the TDR display icon) is on, and uses it to pick the A or B channel setup routine. The TX path calls `FUN_01e5AD68` for RF setup and `FUN_01e5BF2C` to construct the APRS packet. The independent Pi32 decoder shows the table branch, bit-7 read, conditional return paths, temporary bit insertion, and restoration in `output/stock/aprs-tx-select.asm` and `tx-route-dualwatch.asm`. The corrected Ghidra decompilation is in `output/stock/tx-route-fixed-sleigh-existing-project.txt`. This is a **code-path model**, not proof that every timed beacon takes this path or which frequency was transmitted during the A-red display indication. The user has no second receiver or SDR to measure it. Do not patch the route based only on the display color.

`aprs_tx_route_model.py` is a runnable, offline source reconstruction of that switch and its channel-setup call. **Within this selector**, `CHB-Lock` predicts an early return when the current-side bit is A, and B-channel setup when that bit is B, regardless of Dual Watch. `FUN_01e569d2` copies B's frequency and channel state into the working RF state; `FUN_01e568c2` does the same for A (see `evidence/stock/rf-channel-copy.txt`). The APRS TX callback `FUN_01e5a82e` also draws a red rectangle (`0xF800`) using current/display state, but its screen-coordinate and mode conditions are not yet fully resolved. The model does not include the selector's other eligibility checks, display rendering, or physical RF output. Run `py -3 aprs_tx_route_model.py --mode 1 --current-side B --dual-watch` from this folder to inspect the selector; `test_aprs_tx_route_model.py` checks all five cases against the decoded case table. A receiver or SDR measurement near the dummy load, with a known single beacon, remains necessary before changing TX routing.

**Two confirmed entry paths:** the Ghidra-seeded call graph found `FUN_01e5c4e4` (app+`0x05C3E4`) as a caller of the selector. That wrapper checks RAM `0x0000C512` (`PTT Linkage` at clone offset `0x30F6`) and returns unless it equals `1`; its independent Pi32 decode is in `evidence/stock/aprs-tx-select.asm`. A scan of all even stock-app offsets then found a second direct call at app+`0x082F0E` that the seeded graph missed. Its enclosing routine at app+`0x082EB2` reads Timed Beacon at RAM `0x0000C513` (clone `0x30F7`), the 16-bit interval at `0x0000C514`, and a counter at `0x00011CEC`. When enabled, it increments the counter and compares it with `interval * 100`; at the threshold it resets the counter and, unless a state/priority guard skips it, calls `FUN_01e5c3d4` **directly**, bypassing the PTT Linkage wrapper. `scan_pi32_calls.py` also located the scheduler caller at app+`0x087494`. The exact stock-hash-checked disassembly is in `evidence/stock/aprs-timed-beacon.asm` and `aprs-timed-caller.asm`; `aprs_timed_beacon_model.py` reconstructs the threshold and guard. The scheduler period and the meaning of RAM `0x00011B1E` in that guard remain unverified.

Thus a timed beacon **can reach the five-case CHB-Lock selector** even with PTT Linkage off, provided the timer's state/priority guard allows it. The previous statement that this selector was exclusive to PTT Linkage was wrong because the seeded Ghidra graph omitted the scheduler code. The observed A-red display is still not a measurement of RF frequency, and we have not proved which current-side bit value was present at the instant the scheduler called the selector. The next TX trace is the timed caller's Dual Watch state update and the selector's RF setup after it returns.

The bench comparison now has a specific explanation to test: with Dual Watch off and A selected, the current-side bit may remain A, so B-Lock returns before TX; with Dual Watch on, the scheduler may run while that internal bit is B even though A remains the highlighted display line. If so, B RF setup and an A-red display could coexist. This is an inference from the code and screen observations, not a measured RF frequency or a proven state capture. The independent decode of app+`0x05A516` in `evidence/stock/aprs-channel-state.asm` confirms that another routine clears or sets bit 7 of RAM `0x00011B50` when its working frequency matches the stored A or B frequency, respectively. The bit update is now ported in `replacement-source/main/h9_main_aprs.c`; it checks A first if both stored frequencies equal the working frequency and preserves all other bits. The conditions for this routine to run and its relationship to Dual Watch remain unresolved. The timer caller at app+`0x087494` also checks receive/busy state before invoking the scheduler; those flags and the display callback need further tracing.

The CHIRP saved-image layout and corrected main-image references agree on a linear APRS-config offset: `runtime RAM address = clone-image offset + 0x941C` for at least these fields. `0x3084 → 0x0000C4A0` is APRS Switch; `0x30F6 → 0x0000C512` is PTT Linkage; `0x3116 → 0x0000C532` is APRS RX CH; `0x3117 → 0x0000C533` is APRS TX CH; and `0x3118 → 0x0000C534` is PTT priority. The newly decoded timer directly reads Timed Beacon at `0x30F7 → 0x0000C513` and its interval at `0x30F8 → 0x0000C514`. The packet-processing path directly reads APRS RX CH. The earlier Ghidra data-reference report missed these reads because it did not define either routine. Read-only references are in ignored `output/stock/aprs-config-runtime-refs-fixed.txt` and `aprs-settings-refs-fixed.txt`, supplemented by the independent assembly above. The mapping is an analysis aid, not proof that a new setting can be inserted safely without updating serialization, menu tables, and the separate APRS controller.

The original Ghidra-JieLi Pi32v2 SLEIGH source misdecodes the 32-bit unsigned-byte-load offset: `pi32v2_ins_loadstore.sinc` shifts `imm2427` by eight, while the independently documented instruction encoding and byte sequence require four. For example, stock bytes `50 EE 0C 01` at `0x01E58E5C` read `[r0+0x1C]`, but the original Ghidra project labeled them `[r0+0x10C]`; that incorrectly named `0x00011AEC` as `0x00011BDC`. The same defect mislabeled `0x00011B50` as `0x000122D0` in this path. `fix_jieli_byte_offset.py` applies the one-line source correction to a local JieLi processor module with an original-file backup. The local `.sla` was rebuilt, and a **fresh** Ghidra project `H9mainFixed` was imported and analyzed. Its corrected data references in ignored `output/stock/tx-state-refs-fixed-project.txt` now point to `0x00011AEC` and `0x00011B50` from the APRS TX route and show no refs to `0x000122D0` in the scanned code. The original `H9main` project and its data-reference reports retain stale addresses. Earlier findings inferred from those original data cross-references need reevaluation.

## Firmware delivery

The main application is packaged inside `TD-H9-V1.0.38.fw` and is flashed through the BR23 USB mass-storage bootloader. The separate controller has its own `APRS-1.0.15.bin` and bundled `Upgrade.exe`. Decompilation of `_update.Form4` shows a serial COM-port update path: 38400 baud by default, 8 data bits, no parity, one stop bit, DTR and RTS enabled, and 128-byte firmware blocks. `write()` constructs `TID 00 <payload-length+5> 03 <image-offset:u32be> <payload> <sum8>`, with `sum8` over bytes starting at the zero after `TID` through the payload. It sends offsets starting at zero, not `0x08002000`. `writeHandle()` expects a seven-byte reply with status `0x13` at byte 5, then sends `TID 00 01 FF 00` and expects status `0x10`. The vendor's write-reply condition accepts **any** seven-byte response due to an OR expression; the reconstructed tool validates prefix, length, status, and checksum instead. That stronger reply structure is plausible from the request framing but has not been captured from the radio.

The new `aprs_flasher.py` supports offline `inspect` and `plan`, plus an experimental `flash` command using pyserial on Windows or Linux. Its simulated transport tests pass, but no physical APRS module transfer or recovery has been tested. The exact cable and APRS update mode remain to be confirmed. No read-back or backup command was found in `_update.Form4`; do not infer that the APRS module can be restored from the existing main-radio backup. The main `firmware-research/h9-flasher/h9_flasher.py` still accepts the stock `.fw` by default; its explicit `--stock-base` path validates a byte-exact app-only custom repack and records a recovery manifest. It cannot flash an APRS `.bin`. Whether the mute ultimately needs only a main `.fw` or coordinated updates to both images depends on locating the decoder tap and speaker gate. Current evidence points toward the main image for the speaker control, but this is still a hypothesis.
