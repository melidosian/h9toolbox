# TD-H9 v1.0.38 firmware research

## Startup logo resource

The corrected Pi32 decompilation identifies `gImage_logo` as entry zero of resource bank 5. Its declared length is `0xA000` bytes, exactly 128 × 160 × 2, and the generic image renderer reads 16-bit pixels row by row. Bank 5 has logical base `0xA00000` in the main app's resource table. This is **outside** the `0xDA000`-byte main `.fw` flash payload, so replacing bytes in that package cannot replace the logo. The physical storage layout and write protocol for resource bank 5 have not been validated on this radio.

`make_boot_logo_patch.py` converts an image to a 128 × 160 RGB565 candidate, writes a raw pixel file and an IPS patch addressed to logical `0xA00000`, and creates a visual preview. The little-endian RGB565 encoding is still an inference pending a stock resource dump. Neither output is directly flashable with `h9_flasher.py`; the IPS patch is only suitable for a full resource image proven to use the same zero-based logical address map. It never connects to or writes the radio.

```powershell
py -3 firmware-research/h9-firmware-research/make_boot_logo_patch.py 'C:\path\to\logo.png' --trim-white --output-prefix firmware-research/h9-firmware-research/output/my-logo
```

For pixel art, use `--resample nearest` to keep hard edges. The supplied 1122 × 1402 KD9CRQ artwork was converted with that option to ignored `output/kd9crq-pixel-boot-logo.{rgb565,ips,preview.png}`. Its 128 × 160 preview was checked visually. A lower-level read routine adds the bank-5 base address to the logo offset and passes it to ROM routine `0x02001634`; that ROM behavior and the resource-flash device are not yet mapped. Do not apply the IPS file to the 1 MiB main firmware backup or the `.fw` package.

A read-only BR23 probe with loader targets 4 and 5 returned device type 3 and JEDEC ID `0x856014` in both cases, the same 1 MiB primary firmware NOR. Each capacity check stopped before reading logical `0xA00000`. `probe_resource_flash.py` accepts `--target 4` or `5` and saves a 40 KiB region only if the discovered NOR is large enough. It never issues flash erase/write commands. `inspect_logo_region.py` can render a saved region as both RGB565 byte orders for comparison with the radio's actual stock logo. The app's seven resource-bank lengths sum to 16 MiB, and a [first-hand TD-H9 board photo](https://viva-telecom.org/17705/tidradio/td-h9/fotos/28930/) identifies a 16 MB 25Q128 chip. [JieLi's external-flash update documentation](https://doc.zh-jieli.com/Tools/zh-cn/mass_prod_tools/burner_1tuo8/extern_flash_burn.html) describes separate chip-select configuration and `res.bin` packaging for this SoC family; neither is supplied in the stock TD-H9 update package.

The user read the entire primary 1 MiB NOR to `<private-backup-directory>\h9-full-before-logo-mod.bin` (SHA-256 `2c6336b8b2c2a1549946e248a26624ef8f9f2189cf27d4bc1c54d17907af1359`); a second identical copy was saved nearby. Its first `0xDA000` bytes match stock firmware, its settings sector at `0xDA000` contains data, its `0xFD000` sector contains metadata, and `0xF0000..0xF9FFF` is currently erased. That 40 KiB slot is inside the VM reservation and **may be used by the radio later**.

The experimental *internal-logo* route **failed on hardware**. The first bank-5 image descriptor was enlarged by the difference between old base `0xA00000` and internal slot `0xF0000`; bank 5's base and capacity were adjusted by the same difference. `build_internal_logo_probe.py` produced an image that passed offline checks. `flash_internal_logo_probe.py flash` wrote 14 sectors and verified the entire 1 MiB readback against target SHA-256 `62b3af328050c340a3e1257f8966cc76fc48aea0d7f927f868abe49b19b346c7`. After power cycling, the radio showed a black screen. **Do not flash this image again.** The original full-chip backup (SHA-256 `2c6336b8b2c2a1549946e248a26624ef8f9f2189cf27d4bc1c54d17907af1359`) and duplicate remain intact in Downloads. The normal app's write permission mask rejects resource bank 5, so its existing settings writer cannot change the external logo directly.

**Recovery completed through USB HID.** Holding PTT + 2 while powering on with USB-C connected gave a green top LED, blank screen, and a `4C4A:4155` vendor HID interface with 64-byte input/output reports. A generic VID/PID alone was insufficient to identify the protocol, but the `app_dir_head` query reconstructed from [JieLi's HID updater source](https://github.com/Jieli-Tech/fw-Bootloader/blob/ff3b9299d1b94d834b995fd858b3f75e2faa9840/update_tools/win-usb_hid/main.cpp) returned status zero, app address `0x5000`, erase offset zero, and 4 KiB sectors. Read-only CRC requests proved that app-relative offset zero maps to physical primary-flash `0x5000`. All 251 accessible sector CRCs matched the failed image before restoration. `restore_logo_over_hid.py` accepted only the pinned backup/target/manifest, erased and rewrote the 14 changed sectors (app header last), verified each sector, and then matched all 251 accessible sector CRCs to the original backup. The user power-cycled normally and confirmed the usual channel screen and saved channels returned. HID exposes per-sector CRCs rather than a full byte readback; the first `0x5000` bytes were not accessible through this HID file interface and were never changed by the failed image. The earlier full-byte readback of the failed image and pinned original backup hashes remain separate evidence.

For recovery, the separately packaged CH340 `TD-H9-V1.0.38.bin` is byte-for-byte identical to the stock `0xDA000`-byte main firmware payload (SHA-256 `74243eaed19fe0c3e5fbb3ef3c46442f71ee8f7c216f214d322894d26ce4e648`). Its supplied tutorial says to hold PTT + 1 while powering on, connect the two-pin CH340 cable, choose 1,000,000 baud, leave UPDATE UBOOT unchecked, use key 12345678, and select the `.bin`. The user's first two-pin cable identifies as a Prolific PL2303TA (`067B:2303`). On Windows 11, current Prolific driver 3.9.7.0 displayed an unsupported-chip message; Microsoft-signed legacy driver 3.8.31.0 bound successfully as COM5. The second two-pin cable identifies as FTDI (`0403:6001`) and bound as COM6. The radio showed a green top LED and black screen after PTT + 1. With each cable, 1,000,000 baud, `12345678`, Update UBOOT unchecked, and the stock `.bin` selected, the serial updater stopped at `send device init cmd: app_dir_head` with `timeout`, **before any erase or write**. Both cables are generic Baofeng-style cables with no known successful TD-H9 programming history; physical cable compatibility remains unverified. If a serial update restores normal boot and BR23 access, read and verify the full flash before attempting to restore the original 1 MiB backup. Do not assume the serial updater preserves settings or the unused tail.

`probe_serial_recovery.py` is a limited serial diagnostic for this failure. It verifies the selected USB ID, opens the port at 1,000,000 baud/8N1 with DTR and RTS off, sends only the 25-byte `app_dir_head` request recorded from `updata.exe` with key `12345678`, and records the reply. It has no erase or image-write command. The first hardware run on FTDI COM6 in the PTT + 1 green-LED state returned zero bytes after five seconds, independently matching the vendor timeout. A second vendor attempt after entering green-LED mode before inserting the FTDI two-pin plug also timed out at `app_dir_head`. A further custom probe on the radio's USB-C COM4 interface (`4C4A:4155`, PTT + 3) likewise returned zero bytes. No serial probe changed the radio's flash. These failures did not establish whether the two-pin cable wiring, radio mode, bootloader, or another connection detail was responsible. `probe_hid_recovery.py` and `restore_logo_over_hid.py` are the distinct PTT + 2 HID path, using `hidapi` and no serial port.

This directory is a reproducible starting point for TD-H9 firmware modifications. It does **not** contain the manufacturer's original source code or a complete decompilation. `app.bin` is Pi32v2 machine code mixed with data. The scripts extract the known image, validate its JieLi file headers, rebuild the container checksums, and map APRS strings. Generated firmware bytes are ignored by Git under `output/`.

## Current evidence

- Official input: `TD-H9-V1.0.38.fw`, SHA-256 `c4d0beb5281f3a06d7a56083e1744b925f78ff9917c8364e006418ff0bbd0cd6`.
- Outer UFW `flash.bin`: file offset `0x200`, length `0xDA000`, SHA-256 `74243eaed19fe0c3e5fbb3ef3c46442f71ee8f7c216f214d322894d26ce4e648`. Its outer CRC16, header CRC16, and entry-list CRC16 validate.
- Decrypted `app.bin`: flash offset `0x5100`, length `0xD3C2C` (867,372), SHA-256 `11a07bc0b7f23ba809451256004f26e31547f1c251bbbc5f02ef905c968f9cd3`. Its decoded JLFS data CRC16 and ASCII MD5 record validate. The `app_area_head` declares entry address `0x1E00100`; treating that as the start of the app's virtual address mapping is an inference.
- The full stock `.fw` rebuilt from extracted `app.bin` is **byte for byte identical** to the supplied file. A one-byte offline edit rebuilds the app CRC, MD5, parent CRC, and outer UFW CRCs and passes the parser. Neither result establishes that a modified app will boot.
- The decoded app has 46 case-insensitive `APRS` string hits across multilingual UI text, including `APRS Switch`, `APRS On/Off`, and `APRS RX CH`. Literal pointer references cluster in a language string table around app offset `0xCC000`. These are UI/data references; the receive decoder and speaker-audio branch are not identified yet.
- The pre-update radio backup declared its reserved `VM` region at flash `0xC8000`; v1.0.38 declares `VM` at `0xDA000`. The original `0xC8000` sector contained structured radio identity/settings data; the other overlapping sectors through `0xD9FFF` were `0xFF`. The original sector survives in the backup. No VM migration has been validated, so do not copy it into the new VM location without a full flash dump and format analysis.

## Reproduce the extraction

Run from the repository root with Python 3.10 or later:

```powershell
py -3 firmware-research/h9-firmware-research/firmware.py extract 'C:\path\to\TD-H9-V1.0.38.fw' --output firmware-research/h9-firmware-research/output/stock
py -3 firmware-research/h9-firmware-research/firmware.py repack 'C:\path\to\TD-H9-V1.0.38.fw' --app firmware-research/h9-firmware-research/output/stock/app.bin --output firmware-research/h9-firmware-research/output/stock-roundtrip.fw
py -3 -m unittest discover -s firmware-research/h9-firmware-research -p test_firmware.py
```

`extract` and `repack` refuse to overwrite an existing destination. The repacker accepts only this exact stock v1.0.38 package and a replacement `app.bin` of the same size. The [flasher](../h9-flasher/README.md) has an explicit `--stock-base` path that verifies the entire candidate is exactly an app-only repack and saves a backup manifest for custom recovery. A one-byte diagnostic main image has now been flashed and booted, but its APRS behavior is unverified; package integrity alone does not establish runtime correctness.

The pre-update backup is a raw `flash.bin`, not an outer UFW package. Extract it separately to compare its older application and the saved VM overlap:

```powershell
py -3 firmware-research/h9-firmware-research/firmware.py extract-backup 'C:\path\to\h9-before-update.bin' --output firmware-research/h9-firmware-research/output/preupdate
```

## APRS and Pi32 work

The requested first mod is an **APRS mute option that silences received data bursts on both the built-in speaker and Bluetooth audio while continuing to decode and display packets**. The correct hook must preserve the decoder input while silencing the APRS channel's audible output before its speaker/Bluetooth split, or control both outputs independently. A global DAC mute could silence voice or alerts too, and a receive-channel off switch would stop decoding; neither is a validated implementation of this option.

The TD-H9 Ham manual in the community repository lists `APRS Switch`, `APRS RX CH` (Off / CH-A / CH-B), and `RX Decode Tone` (a beep after successful decoding). It does not list an APRS data-audio mute. `RX Decode Tone = Off` only addresses that success beep; `APRS RX CH = Off` disables the chosen receive path. An opt-in audio gate for the configured APRS RX channel, placed downstream of the decoder tap but upstream of both audible outputs, is a candidate. That could also silence voice on the selected channel while enabled; the exact timing and voice behavior need hardware validation.

TIDRADIO also publishes a [separate APRS firmware update procedure](https://www.youtube.com/watch?v=a8ximsXVtJw). The supplied main `.fw` contains APRS menus, but this does not establish where the decoder or speaker gate runs. The two extracted main applications have 40 and 46 APRS string matches respectively; the six additional matches in v1.0.38 are Thai translations, not evidence of a new APRS audio feature.

The user identified the community [teedubyeah/TDH9 repository](https://github.com/teedubyeah/TDH9/tree/1ccb67c2684204b0097533486c545607caaf65b8/APRS/APRS-1.0.15), which includes `APRS-1.0.15.bin` and `Upgrade.exe`. The APRS image is 17,304 bytes, SHA-256 `1dbbc10425f186f22a4d82d73f139f1e3cc3388931b73eb8ed18b6e3087ccd33`. A local copy is retained under ignored `output/aprs-1.0.15.bin`. It is a **separate Cortex-M Thumb image**, with a vector table at inferred flash base `0x08002000`, initial stack pointer `0x20001A50`, reset vector `0x080020D5`, and an `APRS Module Version Info` string. It contains literal addresses consistent with ADC, DMA, timers, and UARTs on an STM32-style memory map. This makes a separate APRS processor plausible; the exact chip and its responsibility for receive audio remain unconfirmed. The bundled updater is a .NET Framework 4.0 PE/CLI assembly according to REA static metadata inspection. We did not execute it.

`analyze_aprs_module.py` validates the exact image hash and writes its vector, selected string, and peripheral-literal map. Clone the repository to a separate directory and pass the `.bin` path:

```powershell
py -3 firmware-research/h9-firmware-research/analyze_aprs_module.py firmware-research/h9-firmware-research/output/aprs-1.0.15.bin --output firmware-research/h9-firmware-research/output/aprs-module-map.json
```

`aprs_flasher.py` reconstructs the **separate APRS controller** serial updater. Its `inspect` and `plan` commands are offline, need no extra package, and do not open a device:

```powershell
py -3 firmware-research/h9-firmware-research/aprs_flasher.py inspect firmware-research/h9-firmware-research/output/aprs-1.0.15.bin
py -3 firmware-research/h9-firmware-research/aprs_flasher.py plan firmware-research/h9-firmware-research/output/aprs-1.0.15.bin
py -3 -m unittest discover -s firmware-research/h9-firmware-research -p test_aprs_flasher.py
```

The `flash` command requires pyserial, a separate APRS update-mode serial port, and `--yes`. It allows a same-length custom image only with `--allow-modified`. It creates a new JSONL transfer journal beside the image by default; `--journal C:\path\to\attempt.jsonl` selects another new path. The journal records the image hash, port, each **acknowledged** block, the exit acknowledgment, and any failure. A journal ending at an offset is evidence of partial transfer, not a safe resume point; restart from the beginning only after restoring the update mode. The tool refuses to overwrite an existing journal. **It has not been tested on hardware**, and the vendor updater does not expose an APRS backup/read-back command. The main-radio `.fw` backup does not contain this separate APRS firmware. Confirm the APRS update-mode cable/port, record the module's current version, and establish recovery before trying a write. The decompiled vendor protocol and the tool's assumptions are recorded in [APRS_CODE_MAP.md](APRS_CODE_MAP.md). The stock `APRS-1.0.15.bin` alone does not implement the requested mute.

For selected Thumb instruction ranges, install Capstone 5 in a separate Python environment and add `--disasm 0x080020d4 --length 0x100`. Linear disassembly can include literal pools as false instructions. Neither this map nor the updater metadata reveals an APRS mute implementation. The main firmware and this module need a cross-processor receive/audio trace before editing either image.

`analyze_app.py` produces an APRS string/pointer map. For selected Pi32v2 bytes it can use [pi32v2-isa](https://github.com/jvitkauskas/pi32v2-isa), commit `9a06ab98808e1c368dea1741f4eeb5aa1b388615`, via its Python API. It linearly decodes the selected range; data can decode as instructions. Clone that repository separately and provide its path:

```powershell
py -3 firmware-research/h9-firmware-research/analyze_app.py aprs-map firmware-research/h9-firmware-research/output/stock/app.bin --output firmware-research/h9-firmware-research/output/stock/aprs-map.json
py -3 firmware-research/h9-firmware-research/analyze_app.py disasm firmware-research/h9-firmware-research/output/stock/app.bin --isa-repo 'C:\path\to\pi32v2-isa' --offset 0 --length 0x1000 --output firmware-research/h9-firmware-research/output/stock/entry.asm
```

The stock app entry decodes plausibly as Pi32v2, but function boundaries and hardware behavior need corroboration. A portable Ghidra 12.1.4 setup with the partial [Ghidra-JieLi](https://github.com/quarkslab/ghidra-jieli) Pi32v2 processor module has now analyzed the main app and the separate ARM APRS image. See [APRS_CODE_MAP.md](APRS_CODE_MAP.md) for the current function/command map and the included read-only Ghidra scripts. The main DAC routines found so far are generic; no APRS-specific speaker gate or safe patch offset has been identified. The [JieLi AC695N SDK](https://github.com/qqq5127/AC6951/blob/AC6951C/cpu/br23/audio_common/app_audio.c#L606) has audio mute APIs that are reference material, not TD-H9 function identifications. The [community TD-H9 v1.0.33 patcher](https://github.com/mjwgeek/TIDRADIO_TD-H9/blob/main/tools/patch_td_h9_v1033.py) documents the checksum chain, but its hardcoded code offsets do not apply to v1.0.38.
The local Ghidra-JieLi Pi32v2 module initially decoded some long byte-load offsets incorrectly, which produced wrong RAM variable names in earlier reports. `fix_jieli_byte_offset.py` patches that one confirmed SLEIGH expression, preserving a copy of the original source; after recompiling `pi32v2.slaspec`, newly decompiled functions agree with the independent Pi32 decoder on the APRS TX route. The main app was freshly imported into `H9mainFixed` to rebuild correct data references; older reports from `H9main` still have stale addresses. See the correction and examples in [APRS_CODE_MAP.md](APRS_CODE_MAP.md).

`H9FunctionStarts.java` exports Ghidra's currently recognized function entrypoints. The independent decoder can then build a partial direct-call index (output is ignored by Git):


This index located the radio AF register `0x47` selector and a separate audio on/off request, described in [APRS_CODE_MAP.md](APRS_CODE_MAP.md). Neither is an identified safe APRS mute patch until the decoder's analog tap and the selected receive channel are traced.

For the 55,928-byte Pi32 code copied to RAM address zero during main startup, decode a selected RAM-address range with the hash-pinned `analyze_main_ram.py` tool. Its output belongs under ignored `output/` and can include data interpreted as code:

## Speaker-gate bench probe (not the APRS mute option)

`build_audio_gate_probe.py` makes a reproducible diagnostic **main** `.fw` from the exact stock v1.0.38 package. It changes one instruction before the GPIO output writer so **each call to that writer** drives index 3 low. The caller can skip the write when its stored state already matches a request, so the patch does not guarantee a continuously low GPIO pin. The independent Pi32 decoder confirms the replacement instruction is `r1 = 0`, and the resulting package passes app-only validation. The radio booted with this image. The user heard APRS and RF traffic through Bluetooth; after Bluetooth audio was disconnected, the built-in speaker remained silent. The original image was restored and the user confirmed that the built-in speaker audio returned. A newly decoded APRS packet under the probe was not confirmed. This probe does not meet the requested mute behavior because Bluetooth still carried the bursts, and it does not add a menu option or a CH-B-only mute.

The generated package in ignored `output/gpio3-low-probe.fw` has SHA-256 `c8b7b896db1a26e279f52d08a9e884041fe7c5640aeb235f04e7f391915fcead`. Its flash payload differs from stock in 40 bytes across three 4 KiB sectors (`0x5000`, `0x57000`, `0xD9000`); the boot area before `0x5000` is identical. Rebuild and inspect offline with:

```powershell
$stock = 'C:\path\to\TD-H9-V1.0.38.fw'
py -3 firmware-research/h9-firmware-research/build_audio_gate_probe.py $stock --output 'C:\path\to\new-gpio3-low-probe.fw'
py -3 firmware-research/h9-flasher/h9_flasher.py inspect 'C:\path\to\new-gpio3-low-probe.fw' --stock-base $stock
```

The pre-probe backup and recovery manifest exist at `<private-backup-directory>\h9-before-gpio3-probe.bin` and its `.json` neighbor. The backup SHA-256 is `74243eaed19fe0c3e5fbb3ef3c46442f71ee8f7c216f214d322894d26ce4e648` and it exactly matches the stock v1.0.38 flash payload. The first flash attempt failed during the initial read with `WinError 31` before any erase; a retry after re-entering update mode wrote three sectors and verified the entire 892,928-byte readback (SHA-256 `cfe64041819ab306598435994c683b31003fc97e2550bc9285d7348932f60c01`). The user reported a normal boot, Bluetooth audio carrying APRS bursts and RF traffic, and silence at the built-in speaker even after disconnecting Bluetooth audio. APRS → Beacon List was empty. The exact logs are ignored under `output/probe-*.log`.

`restore_audio_gate_probe.ps1` then restored the exact pre-probe image, rewriting three sectors and verifying the full readback against the backup SHA-256. The user confirmed normal boot and restored speaker audio after power-cycling. A stock-firmware Beacon List observation after a received burst is still pending. This stock control is necessary before attributing the empty list to the diagnostic patch. Keep CH-A off any voice repeater: the earlier unintended APRS TX on A is unresolved.

`build_af_selector_probe.py` now creates a second **offline-only** main-firmware diagnostic. It forces radio AF register `0x47` to its mode-zero value at the common selector. The generated `output/af-selector-mute-probe.fw` passes exact stock-derived app-only validation (SHA-256 `c0a7c66211e16c5c12790f984013755b4e2978be698601d959319ad6ac79be6d`). It has **not** been flashed. This could silence Bluetooth as well as the local speaker, but it could also starve the separate APRS decoder and would affect all voice receive audio. The stock decoded-packet baseline is needed before a hardware trial. It is not the requested APRS mute option.

On the radio, received stations are under **MENU → APRS → Beacon List (item 6)**, according to the [TD-H9 manual](https://manuals.plus/ae/1005011633543760) and [AA4TE field guide](https://qsl.net/aa4te/tdh9.html). The field guide reports per-station reception counts; record a count, hear a later burst on Bluetooth, and verify that the count increases. A nonempty list alone could predate this diagnostic flash and is not enough to prove continued decoding.

The requested REA firmware-region inspection was attempted on the supplied `.fw`. This Windows REA session reported `capability_unavailable`: that integration requires Linux and a caller-supplied Binwalk path. REA's raw-binary architecture selector does not offer Pi32v2. It admitted the separate ARM image as a raw target, but no configured provider accepted raw ARM analysis on this Windows host. The local format parser, Pi32 decoder, ARM image mapper, and optional Capstone disassembly provide the evidence above; they are not a substitute for a complete decompilation.

## Optional full radio dump

`dump_full_flash.py` reads the radio's entire 1 MiB SPI flash into a **new local file** after checking its bootloader, flash ID, chip key, and image header. It loads a helper into RAM but does not erase or write flash. This would let us inspect the new VM area and the preserved `key_mac` sector. It requires USB update mode and Administrator PowerShell on Windows; recheck the physical drive number first. The dump includes radio identity and settings, so keep it private and outside the repository.

```powershell
py -3 firmware-research/h9-firmware-research/dump_full_flash.py 'C:\path\to\TD-H9-V1.0.38.fw' --device '\\.\PHYSICALDRIVE1' --output 'C:\path\to\h9-full-after-update.bin'
```

The user has configured APRS RX on CH-B at the APRS frequency with Dual Watch enabled. The radio is back on stock main firmware after the GPIO3-low trial. A confirmed incoming packet and a stock Beacon List observation are needed to establish the receive/decode baseline before interpreting the empty Beacon List seen during the trial. A separate operational comparison with Dual Watch off may reveal an existing workaround, but the manual does not establish whether CH-B decoding continues in that mode. The main image now has a confirmed read of `APRS RX CH` in a packet-processing filter at app+`0x086180`; see [APRS_CODE_MAP.md](APRS_CODE_MAP.md). Next code milestones: trace from that filter to the APRS-module UART path, identify the decoder's analog tap and the Bluetooth audio feed, then add an opt-in setting that silences the APRS channel on both audible outputs without starving the decoder. Verify packet decode, voice on the other channel, alerts, persistence, and recovery. The GPIO3-low diagnostic image is not the requested APRS mute option.

`inspect_aprs_config.py` is a read-only helper for saved TD-H9 clone images. For example, run `py -3 inspect_aprs_config.py "C:\\path\\to\\TD-H9-backup.img"`. It prints only the selected APRS control values, their saved-image byte, and a file hash; it does not connect to the radio. The field offsets and enum order follow the [CHIRP TD-H9 test driver](https://chirpmyradio.com/attachments/16094/tdh8.py). Ten saved images from 2026-11-03 all record `CHB-Lock`, APRS RX on B, PTT Linkage off, both DIGI enables off, and Timed Beacon on at a 60-second interval. These are historical captures. The subsequent live screen checks and dummy-load observation below are more current evidence. See [APRS_CODE_MAP.md](APRS_CODE_MAP.md).

In a controlled dummy-load beacon test with CH-A 445.390 MHz and CH-B 144.390 MHz, both simplex and Low power, the radio's A line turned red at 445.390 MHz despite `APRS TX CH = CH B-LOCK`. Timed Beacon was turned off immediately afterward. This reproduces the A-side display indication, but does not measure the actual RF output. The main-image timer at app+`0x082EB2` calls the five-value APRS TX selector at app+`0x05C2D4` directly when its interval expires, even with PTT Linkage off. The B-Lock branch still requires a matching internal channel-state bit, so the hardware observation needs further explanation before changing firmware. The code path and evidence are in [APRS_CODE_MAP.md](APRS_CODE_MAP.md).

With Dual Watch on, the A line turned red during that bench beacon. With Dual Watch off and A selected, neither line turned red during a 75-second interval under the same `CH B-LOCK` setting. Timed Beacon is off again, and Dual Watch was restored on. This narrows the visible difference to Dual Watch behavior; a second receiver or SDR was unavailable to verify actual RF frequency. Do not treat the A-red indication alone as proof of the RF channel. The immediate containment remains Timed Beacon off while this is unresolved.

During that test, the user heard APRS audio, observed the CH-A VFO turn red with a repeater frequency displayed, and heard another operator report APRS audio through the repeater. This is strong field evidence of unintended transmission on A, though no independent frequency measurement or settings capture exists yet. The user was instructed to turn APRS Switch off or power down immediately. Do not repeat a beacon test with A on the repeater. The manual exposes separate `APRS TX CH` and `DIGI Forward CH` settings; the latter can forward on A if digipeating is enabled. The community field guide records `CH-B Lock` but says its precise lock behavior has not been tested. Before any future controlled transmit test, inspect Timed Beacon, PTT Linkage, DIGI1/DIGI2, APRS TX CH, and the active VFO; use a dummy load or a non-repeater test configuration. Keep the APRS Switch off until the unexpected TX path is understood.
