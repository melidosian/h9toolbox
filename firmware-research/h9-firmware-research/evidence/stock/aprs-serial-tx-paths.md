# APRS controller serial transmit paths

Source: captured APRS v1.0.15 image, SHA-256 `1dbbc10425f186f22a4d82d73f139f1e3cc3388931b73eb8ed18b6e3087ccd33`. Addresses below come from the ARM decompilation in `evidence/aprs-command-handlers.txt`, `evidence/aprs-tx-send-gate.txt`, and `evidence/aprs-tx-wave-scheduler.txt`. This is static evidence, not a transmitted RF capture.

Serial command `0x00` reaches the send gate at `0x08005760`, then packet encoder `0x0800534C` and the AFSK waveform queue. The replacement `h9_aprs_tx_runtime` models this route, but only accepts a packet while an explicit RF-ready input is true. The diagnostic board entry has no verified RF-ready signal and keeps this input false.

Serial command `0x11`, subcommand `4`, takes a separate route through `0x08005A94` and `0x08002A4C`. The latter reads GPIOB bit 5 through `0x08002964`; when the read equals 1, it calls `0x08002C94`, which reaches the synchronous UART writer at `0x0800476C`. The literal at `0x08002CA8` points to descriptor `0x20000D94`; initialization at `0x08002974` sets its peripheral base to USART2 `0x40004400` (`0x080029C4`) and its baud to `0x2580` (9,600). The separately framed command reply path uses USART1 `0x40013800` at 115,200 baud. Thus `0x11/4` emits the payload bytes raw over USART2, not to the AFSK waveform queue or USART1 reply stream. The replacement dispatcher now gates its distinct auxiliary UART callback on the GPIO read. The diagnostic board entry leaves that callback unset until USART2 board setup is ported. The external device attached to USART2 and electrical meaning of GPIOB bit 5 remain unverified.
