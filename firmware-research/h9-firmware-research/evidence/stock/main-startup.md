# Main Pi32v2 startup trace

Source: captured main v1.0.38 `app.bin`, SHA-256 `11a07bc0b7f23ba809451256004f26e31547f1c251bbbc5f02ef905c968f9cd3`. The virtual base `0x01E00100` is inferred from JLFS metadata. Instruction decoding used Pi32v2 r3; this is static evidence, not a boot test.

At app+`0x000000`, the stock entry first calls app+`0x02D82E` before setting a stack. That leaf routine reads the launch structure through `r0` and copies fields into RAM beginning at `0xE2A0`; its 42 instruction bytes through the final `rts` are matched byte for byte in `main/h9_main_startup.S` by `link_main_check.py`. At app+`0x000004` and `0x00000A`, stock sets both `sp` and `ssp` to decimal `58000` (`0xE290`). The replacement assembler emits the same 12 stack-setup bytes.

Stock then clears RAM from `0xE2E0` for `66036` bytes, ending at `0x1E4D4`. Its preceding `.data` copy has a zero length in this image. A later loop copies `55928` bytes from mapped source `0x01EC628C` (app+`0x0C618C`) to RAM zero, reads `icfg`, clears bits 8 and 9 with mask `0xFFFFFCFF`, writes it back, calls two startup routines, and jumps to `0x01E5FB7C`. The replacement diagnostic runtime calls the equivalent Pi32 assembly sequence immediately after copying its authored RAM code; the link check matches its 12 register-operation bytes against stock app+`0x7E..0x89`. The copied range ends at app+`0x0D3C04`, 40 bytes before the end of the captured app. Its first 64 bytes are zero; bytes from offset 64 decode as Pi32 instructions. This supports a RAM-resident code interpretation, but the vector layout, call targets, and relocation contract still need reconstruction.

The replacement diagnostic linker confines `.data`/`.bss` to the observed `0xE2E0..0x1E4D4` interval and gives authored `.ram_code` up to the observed `0xDA78` bytes at RAM address zero. Its reset path clears the observed RAM interval, copies linker-defined `.data` and `.ram_code`, applies the stock `icfg` mask, consumes the retained boot record, and enters the allocation-bitmap and first memory-window stages of board setup. The first authored `.ram_code` routine is a semantic rewrite of the stock byte-transfer routine at RAM `0x40`; the rest of the 55,928-byte stock RAM region is not reconstructed. See [main-ram-serial-bus.md](main-ram-serial-bus.md). Interrupt vector assignment, device initialization, and application loop are not ported. The linked ELF must not be treated as a bootable update image.

Ghidra and a separate Pi32v2 instruction decode resolve the two calls after the RAM copy. The first target, `0x01E8C1BC` (app+`0x08C0BC`), is a single `rts` in this image. The second, `0x01E5E594` (app+`0x05E494`), reads the 80-byte record at RAM `0x2FF88`, passes 78 bytes starting at `0x2FF8A` to `0x01E4CBEC`, chooses a default low value of `0x5A00` unless the returned value is nonzero and matches the record's **first 16-bit halfword** at `0x2FF88`, combines it with the record's upper halfword at `0x2FF8E`, writes the result to RAM `0x11C3C`, and clears the 80-byte record. The independent decode confirms the caller's `lh.z` comparison; the earlier replacement compared a 32-bit word and was wrong.

The helper at `0x01E4CBEC` calls ROM `0x02002BC4(0x12850, 0)`, zeros `0x001E3504`, streams the 78 bytes as words to `0x001E3500`, executes `csync`, captures the word at RAM `0x12854`, calls ROM `0x02002C3C(0x12850)`, then returns the captured **low 16 bits**. The Pi32 instruction decode confirms that the result is loaded before the cleanup call. Ghidra's pseudocode incorrectly shows a constant zero return; its instruction listing and the independent decode agree on the real return. `main/h9_main_boot_validator.*` ports that sequence with injectable hooks and Pi32 ROM/MMIO bindings. `main/h9_main_boot_record.*` ports the corrected decision and clearing. The diagnostic reset path now passes the retained record at `0x2FF88` through these routines and stores the result at `0x11C3C`, matching the stock order after the `icfg` mask. This order was checked in the linked Pi32 disassembly; neither the record's physical purpose nor runtime board behavior has been validated.

The jump target `0x01E5FB7C` (app+`0x05FA7C`) enters a much larger board initialization routine. Its opening calls ROM entries `0x020000A0` and `0x02003174`, configures memory ranges and registers, initializes stack guard words, then calls further local and ROM routines. The current Ghidra decompilation contains many undefined register return values and removed blocks, so it is only a discovery map, not source to copy directly. The replacement board entry now ports those first two ROM calls, the bounded allocation bitmap and metadata at app+`0x05FA8A..0x05FB64`, the first memory-window stage at app+`0x05FB64..0x05FBF6`, the guard/state-marker writes through app+`0x05FC20`, the four-channel clock helper called at app+`0x05FC20` through its return, the first post-clock ROM block at app+`0x05FC24..0x05FC4C`, hardware-field classification through app+`0x05FCB2`, the selector-192 bitmap branch through app+`0x05FCD4`, and the four descriptor routes after the ROM handoff through app+`0x05FD74`. See [main-heap-bitmap.md](main-heap-bitmap.md), [main-memory-window.md](main-memory-window.md), [main-board-markers.md](main-board-markers.md), [main-clock-probe.md](main-clock-probe.md), [main-clock-apply.md](main-clock-apply.md), and [main-post-clock-board.md](main-post-clock-board.md). Subsequent board initialization and interrupts remain unported.

`analyze_main_ram.py` now disassembles selected ranges as RAM addresses after rechecking the complete stock app hash. The exact copied slice has SHA-256 `de67ad012f5b50d2297d20ccb8c5136badba55b5d7e77ebb2eddf409fa7548b5`; its first 64 bytes are zero, and the first decoded routine begins at RAM `0x40`. Candidate interrupt entries appear at RAM `0x1416`, `0x1A92`, and `0x4356`, where the linear decode finds saved `psr/rets/reti` state. Their vector assignments and whether any produces the APRS UART ring at RAM `0x16E34` remain unresolved. The source tool and private disassembly output distinguish the RAM address from the app file offset, preventing a flash-address interpretation of those routines.
