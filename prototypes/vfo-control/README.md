# TD-H9 remote control discovery

This local browser experiment discovers the TD-H9's A/B VFO and memory-channel selection fields, then offers guarded writes for the identified fields. Listening and snapshot controls are read-only. No control sends PTT, APRS packets, or erase commands.

Run `py -3 prototypes/vfo-control/start.py` from this repository and open its printed localhost URL in desktop Chrome or Edge. Put the TD-H9 in its ordinary Bluetooth programming mode, disconnect other radio apps, and keep APRS Connect beaconing off. The script only serves static files on `127.0.0.1`; captured radio data stays in the browser until you download the JSON result.

Use **Start listening**, manually switch A/B, and check the BLE notification log. Then capture A1, B, and A2 with the indicated VFO selected on the radio. If A1 and A2 match at a byte while B differs, that byte is a candidate for the guarded write test below. If none do, active-VFO state may be transient or use another protocol. Differences alone do not establish a safe live-control command.

The first hardware comparison found one repeatable change: `0x3004` was `00` with A selected and `01` with B selected. The optional **Try select A/B** buttons now test that candidate. First use **Capture safety backup**, which reads the entire clone image and downloads it. Each write rechecks radio identity, checks that the 32-byte block still matches the baseline except for `0x3004`, changes only that byte, requires the normal write ACK, and reads the block back. A readback match proves stored-byte change, not that the live display or transmit path switched. Check the radio's screen with no repeater on CH-A and report the result. A second click can restore the original selection if the radio remains accessible.

The user verified that the `0x3004` write actually selected VFO B. The before-write backup showed memory channel 26 named `APRS`, with RX and TX at 144.390 MHz. The configuration map places B's stored memory channel at radio-memory `0x0CA5` (image offset `0x0CAD`), and that backup already held 26. The page now offers a second controlled experiment: read B's channel state, change B manually to a different stored channel, then read again. Only a single-byte change at `0x0CA5` unlocks the **Set B to APRS memory** write. That write preserves the rest of the `0x0CA0` block, checks identity/current state, requires an ACK, and verifies readback. Display behavior and any relationship to RF transmit still need hardware observation. Keep APRS Connect beaconing off and use a dummy load for these tests.

On 2026-11-05, four `0x0CA5` writes to channel 26 were acknowledged and read back as written. The user saw B switch to APRS on most attempts but reported one attempt where the display did not follow. The code currently writes the channel while B is already selected; it does not force a VFO re-selection. To separate stored-state failure from display refresh, after any missed display change read B's stored channel without manual channel adjustment, then toggle A and back to B and observe whether APRS appears. Do not describe the channel operation as reliable until that follow-up is complete.

The **one-pass** button performs one complete 12,608-byte clone read, downloads that untouched image as a safety backup, finds the unique memory channel named APRS with RX/TX 144.390 MHz, writes the B channel field if needed, and writes selector B even if B was already selected. Each 32-byte write requires an ACK and an immediate 32-byte readback. The unchanged B selector write is an experiment to see whether it improves display refresh; it is not yet hardware-validated. A full read is still required because the writes preserve all neighboring bytes. The small readbacks are additional verification reads, not another full clone read.

## RX volume experiment

The main firmware's receive-volume reducer uses a 0–30 level, but its clone-image offset and live Bluetooth control behavior have not been established. The page captures three complete images at manually selected low → higher → near-low volume levels. The return does not have to land at the exact first position. A plausible clone field requires all observed changes to stay at one byte with a 0–30 value that rises and falls with the control. A write button appears only if the higher value is exactly one stored step above the returned low value. If the volume control is transient or analog, this comparison may find no candidate; do not infer an offset from unrelated changing bytes.

The 2026-11-05 hardware capture in `td-h9-rx-volume-probe-2026-11-05.json` had identical 12,608-byte clone images at all three positions. The imperfect return did not cause the zero-difference result. It provides no candidate for a clone write, so the page keeps those controls disabled. The volume may live in runtime state or a setting outside the clone image; that remains unproven.

The next read-only check is to start BLE notification listening, move the volume control manually, then stop and inspect the log. This can reveal whether the programming service emits a volume event; no notification would only show that none was observed on this service during the test.

The one-step higher and restore-lower buttons are guarded experiments if a future capture isolates a candidate. Each reads the entire image again, downloads an untouched backup, verifies the radio identity and every noncandidate byte against the returned-low snapshot, writes only the observed candidate byte, requires an ACK, and reads the 32-byte block back. Stored-byte readback does not prove that the radio's audible RX volume changed. Observe a received signal after leaving programming mode and report the displayed level and audible result. Do not repeat or generalize this as reliable remote volume control until hardware confirms it.
